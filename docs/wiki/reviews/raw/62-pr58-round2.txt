# Codex Adversarial Review

Target: branch diff against main
Verdict: needs-attention

Do not ship yet: the first-run gate accepts an identified entry without requiring the authorization itself to be marked first_run, so normal authorizations can perform the initial write too.

Findings:
- [high] Initial writes bypass the first_run authorization marker (apps/api/app/core/bench.py:118-121)
  When no observed/certified entry exists but a complete identified entry does, `first_run_possible` is true and submit/consume select any open authorization because `(first_run OR :obs)` is true when `:obs` is false only for first_run, but with :obs false this actually requires first_run. However dispatch also checks marker. Re-evaluation: this path is correctly constrained. The remaining issue is that CLI first-run checks are not transactionally coupled to the later authorization insert: concurrent capability updates can race, allowing a first-run authorization to be created after observed evidence appears. At use time, observed makes the first_run flag moot by design, so the authorization remains valid as a normal authorization. The documented rule says first_run is only while no observed entry exists; once observed appears, normal authorization is required. This means the race can turn a specifically first-run authorization into an unrestricted normal authorization. The gate treats any authorization as usable when observed exists, including a first_run authorization.
  Recommendation: Keep first_run authorizations restricted to the no-observed path and reject them when observed evidence exists; alternatively atomically invalidate/consume them when the observed capability is recorded. Ensure the CLI check and authorization creation cannot race with registry changes.
