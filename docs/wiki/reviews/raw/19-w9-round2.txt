# Codex Adversarial Review

Target: branch diff against main
Verdict: needs-attention

Não enviar ainda: a tolerância aceita replay de token consumido e pode emitir sucessores utilizáveis; o middleware também não renova enquanto o cookie de acesso expirado ainda está presente.

Findings:
- [high] Replay dentro da tolerância emite sucessores válidos (apps/api/app/api/session.py:67-76)
  Qualquer apresentação do refresh token consumido dentro dos 10 s passa pela mesma ramificação de uma corrida legítima e recebe um novo token da família. Um atacante com cópia do token pode fazer várias chamadas nessa janela; cada sucessor emitido continua válido depois que a janela fecha, permitindo manter sessões paralelas e escapar da detecção de replay do token original. O lock serializa chamadas, mas não distingue concorrência legítima de roubo. Reduza o risco vinculando a tolerância à idempotência da operação (por exemplo, devolver o mesmo sucessor para a mesma requisição) ou usando outro mecanismo que não emita novos tokens por replay.
  Recommendation: Não criar outro sucessor para cada replay. Persistir e devolver uma resposta idempotente associada ao refresh original/requisição, ou adotar uma estratégia de rotação que preserve a detecção de roubo sem multiplicar tokens válidos.
- [medium] Refresh não acontece quando o access token expirou (apps/web/src/middleware.ts:11-13)
  O middleware sai imediatamente quando `fc_token` existe, sem verificar sua validade. Como o cookie é mantido até seu `maxAge`, ele continuará presente após o access token expirar; nesse estado o middleware nunca chama `/refresh`, e as chamadas autenticadas redirecionam para login. Assim, a renovação automática não funciona no caso normal de expiração do access token e a sessão efetivamente termina após o TTL de acesso.
  Recommendation: Detectar access token expirado (ou renovar antes do vencimento) e executar refresh mesmo quando o cookie de acesso ainda estiver presente; atualizar ambos os cookies na resposta.
