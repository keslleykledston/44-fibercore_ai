# Codex Adversarial Review

Target: branch diff against main
Verdict: needs-attention

Do not ship yet: speed failures can persist and expose unfiltered Edge detail, and the generic jobs API bypasses speed-specific controls once Edge support is enabled.

Findings:
- [high] Speed jobs can bypass the speed flag and run limits through the generic jobs API (apps/api/app/api/jobs.py:154-156)
  The speed router enforces `speed_diagnostics`, endpoint readiness, PON/CPE slot limits, and run recording, but `/v1/jobs/preview` also accepts these operations through the shared `BENCH_OPS` path. That path does not apply those speed-specific checks, and submit relies only on the bench gate. With `SPEED_EDGE_SUPPORT` currently false this path is blocked at submit; if Edge support is enabled as planned, generic jobs can be submitted without the speed flag, slot limits, or a `speed_test_runs` row. This defeats the documented controls and leaves those tests out of run history.
  Recommendation: Route speed operations through the speed-specific request checks, or enforce the feature flag, endpoint health, PON/CPE/tenant limits, and run creation in shared job submission so every entry point gets the same controls.
- [medium] Unfiltered Edge failure detail can leak addresses into speed run history (apps/api/app/api/jobs.py:445)
  The result handler stores `body.detail` in `jobs.result` without validating it for speed operations. The speed run view then returns that detail for failed or unknown jobs. An Edge error containing a test-node URL, IP address, or other internal target data would therefore be persisted and exposed through the speed history API, despite the stated no-address contract.
  Recommendation: For speed results, accept only a closed set of short reason codes and discard or redact free-form Edge detail before storing or returning it.
