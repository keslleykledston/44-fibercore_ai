# Codex Adversarial Review

Target: branch diff against main
Verdict: needs-attention

Do not ship yet: the synchronous SNMP side channel can consume the remainder of the 10-minute round, and overlapping CLI/SNMP reads can reintroduce stale last-down times after a newer CLI snapshot clears them.

Findings:
- [high] SNMP side channel can starve the collection round (agents/edge/internal/collector/olt.go:180-181)
  `Collect` calls `refreshLastDown` synchronously after each CLI attempt. Its 8-minute budget is capped by the 10-minute round context, but it can still spend nearly all remaining round time waiting on paced SNMP requests. That delays later OLT sources and collectors, and can leave the round canceled before they run; the ignored SNMP error does not prevent this delay. Run the side channel asynchronously or give it a small independent budget that cannot consume the round's remaining time.
  Recommendation: Make last-down refresh non-blocking for `Collect`, or enforce a strict short budget and scheduling policy that preserves time for the rest of the round.
- [medium] An older SNMP response can restore a cleared timestamp (agents/edge/internal/collector/olt_lastdown.go:111-116)
  `ldMu` prevents concurrent map access, but it does not order updates by snapshot age. Because the side channel has a distinct guard key from CLI, overlapping `Collect` calls can run its SNMP request while another call obtains and applies a newer CLI snapshot. If the CLI snapshot observes an ONU online and clears its cached time, the older SNMP response can later write that ONU's offline timestamp back into `st.at`; a subsequent offline CLI snapshot can then inherit the stale time. This can report the prior outage after a bounce. Associate updates with a CLI generation and discard results from older generations, or serialize side-channel updates against CLI state replacement.
  Recommendation: Track a generation/version for each CLI snapshot and apply SNMP results only if the generation has not advanced since the request began.
