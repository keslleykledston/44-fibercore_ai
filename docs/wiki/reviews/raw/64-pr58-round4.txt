No-ship: capability promotion can race dispatch, letting a first-run authorization pass after an observed entry has been committed.

Findings:
- [medium] First-run eligibility is not serialized with dispatch (apps/api/app/core/bench.py:92-120)
  At dispatch, `gate()` reads capability rows to decide `observed`, then separately reads the authorization. Under PostgreSQL’s usual READ COMMITTED isolation, the owner CLI can promote the profile to `observed` after the capability query but before the gate completes; this dispatch can still pass using the earlier snapshot and emit an envelope backed by a first-run authorization. That violates the rule that first-run authorizations are valid only while no observed entry exists. Serialize promotion with dispatch or recheck eligibility in a transaction that prevents this race.
  Recommendation: Make capability promotion and dispatch eligibility mutually exclusive, for example by locking the matching capability row and rechecking it at dispatch, or by using a shared advisory lock around promotion and dispatch gate evaluation.
