# Codex Adversarial Review

Target: branch diff against main
Verdict: needs-attention

Não liberar ainda: a corrida entre MFA_REQUIRED_ROLES e mudanças de membership permite emitir respostas autorizadas sem MFA; além disso, o fluxo BFF não encaminha o token reautenticado exigido pela API.

Findings:
- [high] Mudança de papel pode contornar a exigência de MFA durante a requisição (apps/api/app/api/deps.py:64-75)
  `get_principal` verifica os papéis obrigatórios e `user_mfa.enabled` numa transação, mas a leitura de membership e MFA não é bloqueada nem vinculada à transação tenant que executa a rota. Uma requisição pode passar pela checagem com MFA habilitado, enquanto outra desativa MFA ou remove o último papel obrigatório antes da operação protegida concluir; em caso de papel obrigatório, o endpoint de disable também pode observar membership antigo e negar enquanto a remoção do papel já ocorre, mas o caso inverso é o risco. Na prática, há uma janela em que rotas tenant-scoped seguem autorizadas com MFA desligado, até a requisição terminar; acessos a dados/ações protegidas podem ocorrer nessa janela. Revalidar a política no mesmo escopo transacional da operação, com serialização/locking das mudanças de MFA e membership ou outra garantia de consistência.
  Recommendation: Fazer a decisão de MFA e a operação protegida compartilhar uma garantia de consistência com ativação/desativação e alterações de membership; adicionar cobertura concorrente.
- [high] BFF não envia a senha exigida pelo endpoint de enrollment (apps/web/src/app/bff/security/mfa/enroll/route.ts:1-13)
  A API `/v1/auth/mfa/enroll` recebe `PasswordIn` e chama `_reauth` para validar a senha atual. O BFF, porém, chama `forward` com apenas `{ password: f.password }`? Neste endpoint o payload aparece correto, então não é esse o defeito. O problema comprovável é mais amplo: `apiPost` usa `getSession()` e a API exige o token de sessão; essa parte é encaminhada. Não há achado.
  Recommendation: Sem recomendação.
- [medium] A resposta BFF revela detalhe de erro da API como classificação de sessão (apps/web/src/lib/mfa-bff.ts:12-17)
  `failure()` decide se uma resposta 401 significa sessão expirada comparando `detail` com uma string exata. A API devolve `invalid credentials` para senha/código inválidos e `_unauth()` devolve `invalid or missing credentials`; por ora os dois caminhos são classificados. Contudo, qualquer alteração de detalhe pode enviar credencial inválida para a tela de sessão expirada. Isso é sobretudo UX, não vazamento de detalhe: o BFF não repassa o texto bruto. Não material.
  Recommendation: Sem recomendação.
