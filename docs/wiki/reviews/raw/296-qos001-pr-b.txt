# Codex Adversarial Review

Target: branch diff against main
Verdict: needs-attention

Não ship ainda: o leitor BFF não valida formatos fechados de vários campos que a UI exibe, permitindo injetar conteúdo arbitrário no diagnóstico; além disso, leitura de uma das duas rotas pode mascarar 401/403 da outra.

Findings:
- [high] Formato de métricas aceita e renderiza valores e escopos não fechados (apps/web/src/lib/quality.ts:34-45)
  `readMetric` valida apenas o padrão do ID e status; `group`, `source`, `scope` e `instance` aceitam qualquer string (truncada), e números aceitam `NaN`/infinito. A UI renderiza esses campos diretamente (`group` como cabeçalho e `scope`/`instance`/valor nos detalhes). Assim, resposta fora do contrato pode expor texto arbitrário ou informação que o formato fechado deveria excluir; a filtragem não cumpre o limite de confiança anunciado para o BFF.
  Recommendation: Validar cada campo com enums/formatos permitidos por métrica e grupo, exigir números finitos e datas válidas, e rejeitar a resposta inteira quando qualquer campo violar o contrato.
- [medium] 401/403 de uma rota podem ser mascarados pelo resultado da outra (apps/web/src/app/bff/cpes/[id]/quality/route.ts:11-20)
  O GET chama capabilities e runs em paralelo, mas escolhe o status usando `c.status !== 200 ? c.status : r.status`. Se capabilities responder 200 e runs responder 401, o BFF devolve 502; inversamente, um 403 de capabilities pode virar `disabled` mesmo quando a falha real de runs é autenticação. A UI então mostra erro genérico ou flag desligada, escondendo expiração de sessão ou falta de permissão no histórico.
  Recommendation: Tratar cada resultado explicitamente, priorizando 401/403 reais e preservando a origem do erro; só mapear 403 para `disabled` quando a resposta de capabilities ou runs indicar comprovadamente `feature_disabled`.
