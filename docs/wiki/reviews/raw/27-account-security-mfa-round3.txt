# Codex Adversarial Review

Target: branch diff against main
Verdict: needs-attention

Do not ship yet: concurrent enrollment can overwrite an activation and silently turn MFA back off, including for roles whose access policy requires MFA.

Findings:
- [medium] Enrollment can race activation and disable MFA after it succeeds (apps/api/app/api/session.py:219-226)
  `mfa_enroll` checks `enabled` without locking the row, then its UPSERT unconditionally writes `enabled = false`. If enrollment reads the row while MFA is disabled and activation commits before the UPSERT runs, the UPSERT waits and then overwrites the newly enabled row with a new secret and `enabled = false`. Activation has already returned recovery codes, which remain in the table, but the account is now unprotected; for a required role this also gates the user out of tenant routes. Serialize enrollment with activation/disable and recheck the state after acquiring the row lock, or make the state transition conditional so an enabled row cannot be overwritten.
  Recommendation: Lock the user's MFA row before checking or changing it, and reject enrollment if it became enabled while waiting. Add a deterministic concurrency test that holds the row lock, starts enrollment and activation, then asserts MFA remains enabled and the returned recovery codes match the stored set.
