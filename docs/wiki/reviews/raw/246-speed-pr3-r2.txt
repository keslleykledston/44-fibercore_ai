# Codex Adversarial Review

Target: branch diff against main
Verdict: needs-attention

Do not ship yet: after a run is accepted, a failed or stale post-submit refresh can leave the UI showing no active run and re-enable both test controls while the backend may already be executing it.

Findings:
- [high] Accepted test can disappear after refresh failure, re-enabling duplicate requests (apps/web/src/components/SpeedTestSection.tsx:75-88)
  After POST succeeds, `start` relies on the following `fetchAll()` to reveal the accepted run. If that read fails, it replaces the ready state with an error; when a user retries, or when the fetch returns a stale snapshot, the UI has no active run and its start controls become available again. The POST response is treated as submitted, but its outcome is not retained in UI state. The backend may still have queued or started the test, so another click can submit a second request and generate additional traffic or conflicting operations. The sequence number prevents an older response from overwriting a newer read, but it does not address a failed or stale newest read after acceptance.
  Recommendation: On successful POST, preserve a pending/accepted state and keep both controls disabled until a read confirms a terminal state or a clear failure; distinguish refresh failure from request failure and provide polling/retry without clearing the accepted state.

Next steps:
- Retain accepted request state independently of the latest runs snapshot, and add coverage for POST success followed by failed/stale reads.
