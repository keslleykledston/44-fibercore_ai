# Interoperação real do ADR-0046 (OLT gerenciada): navegador → API → Edge Go (2026-11-12)

Evidência operacional da prova de ponta a ponta do ADR-0046 D4/D6 com o **binário Go real do Edge** (`agents/edge`, sem simulador), a API real com Postgres, o web de produção (`next start`) e um navegador real (Chromium, Playwright). Estado: **pilha efêmera de teste, nunca a LAB**; nenhum gate de produção concedido; nenhuma flag da LAB foi tocada. Todos os valores (senha, community, IPs, impressões digitais) são de TESTE e descartáveis. Nenhum segredo está neste documento.

## Resultado

Execução única de ponta a ponta, em pilha recém-criada (`run.sh up` → `run.sh test` → `run.sh down`): **10 testes, 10 passaram, 14,6 min** (o teste "ambiente" mais as provas 1 a 9). A prova 9 foi repetida uma vez em seguida (só ela, sobre a captura de rede gravada em disco) depois de acrescentar o controle positivo, a busca de IP completo e a consulta ao banco.

## Método

```
Chromium (Playwright) ──► web (next start :28490) ──BFF──► API (compose, Postgres/NATS) :28420
                                                                 ▲
        Edge A (binário Go real, config.json de teste) ──► proxy de teste :28421 ──┘   (org A)
        Edge B (binário Go real, outro config/estado/chave)  ───────────────────────►  (org B)
        Edge A/B ──SSH/SNMP──► sshsink (servidor SSH de teste, registra toda tentativa)
```

- **Pilha efêmera própria:** `COMPOSE_PROJECT_NAME=fibercore-interop46` (`-p` explícito; o script recusa `fibercore-prod` e `fibercore-dev`), portas próprias (API 28420, proxy 28421, web 28490), `docker compose -p fibercore-interop46 … up -d --build api-core outbox-relay job-sweeper event-consumer` (Postgres 17 e NATS vêm como dependências), `down -v` só nela. Migração `alembic_version` = **0051**. `.env.dev` é gerado por `make env-dev` com segredos aleatórios (o `.env` real nunca é lido). Seed: `scripts/seed_demo.py` (org A, `E2E_EDGE_CREDS_FILE`, o mesmo método da interoperação do ADR-0045) e `scripts/interop46/seed_orgs.py` (flags `fleet_manager`, `fleet_provision`, `fleet_secrets` ligadas nas duas organizações; org B com Edge e conta de serviço próprios).
- **Edge real:** `CGO_ENABLED=0 go build -ldflags "-X main.version=0.9.0-interop46" ./cmd/fibercore-edge` do commit `7473e94` (árvore limpa em `agents/` e `apps/`). Dois processos (Edge A e Edge B), cada um com `config.json` 0600, `state_dir` 0700, chave de selagem própria (gerada no primeiro start, publicada, e **confirmada pela pessoa na tela** comparando com `fibercore-edge seal-fingerprint`). `poll_seconds=15`, `collect_seconds=30`. Política do Edge A: `allowed_cidrs` = seis redes /16, `allowed_ports` = 22, 22022, 22023, 16161, `max_olts` = 5 (a OLT estática conta), `allowed_vendors` = `["huawei"]`, `allow_legacy_ssh` = false, `pon_ports` = `["0/1/0"]`, mais uma OLT **estática** (`OLT-ESTATICA-01`, para o `name_conflict` e o `max_olts`). Edge B: só `172.19.0.0/16` (rede que o Edge A **não** libera). O Edge A fala com a API por um proxy HTTP de teste (só loopback) para poder forjar/repetir entregas; o Edge B fala direto.
- **"IP de OLT" roteável localmente sem root:** IPs das pontes docker da máquina (`172.17.0.1` a `172.23.0.1`; não são loopback). O `sshsink` escuta neles (TCP 22022 e 22023; UDP 16161 em `172.22.0.1`).
- **`sshsink`** (`scripts/interop46/sshsink`, módulo Go próprio com `golang.org/x/crypto/ssh`, fora de `agents/edge/internal`): chave de host conhecida, **registra** em JSON cada aceite TCP, falha de handshake (cliente que aborta), tentativa de autenticação (usuário confere? senha confere? **nunca a senha**), comando executado e datagrama UDP (**só o tamanho**). Ele não é uma OLT Huawei: depois de autenticar, a coleta falha no parser (`cannot parse display version`), o que é esperado e só dispara o cooldown do Edge.
- **Navegador:** tudo o que a pessoa faz vai pela tela (cadastro, confirmação da chave do Edge, conexão, credenciais, edição, leitura da prontidão). A API só é usada para **verificar** (estado, 404s do isolamento). O administrador do Edge é o processo de teste rodando `fibercore-edge managed-list`/`managed-trust`/`seal-fingerprint` do binário real.
- **Janela de observação ("≥ 2 ciclos"):** 75 s com `collect_seconds=30` (≥ 2 ciclos de coleta) e `poll_seconds=15` (≥ 4 de entrega); as ausências sempre vêm com um **controle** (mesma OLT, mesmo caminho, depois de confiar: o Edge conecta no ciclo seguinte).

## Reproduzir

```bash
export INTEROP_DIR=/algum/diretorio/de/trabalho      # só valores de teste
export VENV_PY=/caminho/do/.venv/bin/python          # python do projeto (precisa de httpx e cryptography)

scripts/interop46/run.sh test    # Playwright: scripts/interop46/interop46.spec.ts (evidências em $INTEROP_DIR/evidence)
scripts/interop46/run.sh down    # derruba TUDO (compose down -v do projeto próprio, processos por PID/porta, .env.dev, links, build do web)
```

Pré-requisitos: docker compose, Go 1.22 com o cache de módulos que o Edge já usa (o `sshsink` compila offline com `golang.org/x/crypto` v0.31.0), Node 22 com o `node_modules` do `apps/web` (o `run.sh` cria e remove o link) e Chromium do Playwright 1.55.1.

Arquivos: `scripts/interop46/run.sh` (orquestra), `interop46.spec.ts` + `playwright.interop.config.ts` (as provas), `mkedge.py` (monta o `config.json` de um Edge de teste; deriva a chave pública dos jobs da semente do `.env.dev` sem ecoá-la), `edgeproxy.py` (proxy de teste: `tamper_sealed`, `tamper_sig`, `tamper_olt`, `replay`), `sshsink/` (servidor SSH/UDP de teste), `seed_orgs.py` (flags e org B). Uma prova isolada: `scripts/interop46/run.sh test --grep "prova 3"` (o estado fica em `evidence/state-run.json`; as provas dependem das anteriores).

## Achados

**Defeitos de implementação (Edge, API, web): nenhum.** Os três tropeços durante o desenvolvimento da prova eram do próprio teste e foram corrigidos nele (PID do Edge gravado errado no script de partida; um marcador de observação tirado depois do reinício do Edge, que perdia a primeira conexão; e a expectativa de que a prontidão fosse "confiada" quando, com a credencial já aplicada, a tela corretamente avança para "credencial aplicada").

Observações para decisão (nenhuma bloqueia; não foram "corrigidas"):

1. **Ritmo do Edge vs. a frase de `managed-trust`.** `managed-trust` diz "É coletada a partir da próxima rodada". Para uma OLT nova isso vale (prova 3: a conexão veio no ciclo seguinte). Mas o guarda de ritmo é **por IP** (`config.DeviceKey` ignora a porta) com intervalo de 15 min e cooldown de 15 min depois de uma coleta que falhou: uma OLT já coletada há pouco, ou que falhou, e que o administrador confia de novo (por mudar a porta ou a impressão digital) só reconecta quando o guarda liberar. Na prova 4 isso foi contornado reiniciando o Edge (o guarda é persistido em `olt-guard.json`). Sugestão: dizer isso no texto do comando e em `EDGE_MANAGED_OLTS.md`.
2. **Sem caminho na tela para `remove`.** O contrato (D4/D6), o Edge e o selador do navegador suportam `action:"remove"`, mas nenhuma tela o aciona hoje; só foi provado pelo selador de produção via BFF. Se for desejado, é uma decisão de produto (botão "Remover do Edge").
3. **Identidade por IP.** Duas OLTs gerenciadas com o mesmo IP e portas diferentes são tratadas como o mesmo dispositivo (`name_conflict`), coerente com `DeviceKey` e com o doc do Edge; vale lembrar na tela de cadastro de quem tem uma OLT com dois serviços.
4. A mensagem do `managed-trust` e a do log do Edge mostram a impressão digital que o servidor **realmente** apresentou quando recusa a chave (`host key mismatch (got SHA256:…)`): útil para o administrador comparar, e não é segredo.

## Limites (o que esta prova NÃO cobre)

- **Nenhuma OLT de verdade.** O servidor SSH de teste não é Huawei/ZTE: a coleta depois da autenticação falha no parser, como esperado. Não se provou parse, snapshot nem ingestão de uma coleta de OLT gerenciada de ponta a ponta, nem SNMP real (o UDP de teste não responde; só se prova que o Edge **envia** pacotes depois da confiança).
- **`remove`**: sem botão na tela; provado com o selador de produção por BFF (ver acima).
- **Forja e replay no Edge** foram feitos com um proxy de teste entre o Edge A e a API (a API verdadeira nunca emitiria isso). O replay **na API** foi o `delivery_id` reenviado pelo navegador (409 `delivery_id_taken`).
- **MFA recente** (`mfa_recent` em `fleet:provision`) não foi exercida: a pilha usa o padrão `MFA_RECENT_ENFORCE=false`. **CSP, nginx do host e HTTPS** não fazem parte (web em `http://127.0.0.1`, que o navegador trata como contexto seguro, necessário para o WebCrypto).
- **Prova 9:** o log do web (`next start`) só tem o banner de partida (260 bytes), então ele prova pouco; os logs da API (~155 KB, `docker compose logs` de todos os serviços), do Edge A/B, do proxy e do `sshsink` têm conteúdo real. A varredura procura a senha e a community de teste, o usuário de teste e os blobs selados que o navegador enviou (25 na execução completa, que inclui o do `remove`; 24 na repetição, que lê a captura de rede gravada em disco) (mais um **controle positivo**: o mesmo método de busca acha a senha 1x no arquivo de credenciais do Edge). Não varre a memória dos processos, o disco do Postgres nem o histórico do navegador. Tem o limite de qualquer varredura por valor exato: um formato transformado (por exemplo, a senha em base64 num log) não seria achado.
- **Ritmo e tempo:** a janela de 75 s é "≥ 2 ciclos" nos parâmetros de teste (`collect_seconds=30`, `poll_seconds=15`); em produção os intervalos padrão são maiores (300 s de coleta, 15 min por OLT).
- **Uma só máquina:** Edge e "OLT" no mesmo host, em IPs de pontes docker; não se provou nada sobre rede real, NAT, latência ou o systemd do Edge.
- **Chrome único:** Chromium 140 (Playwright 1.55.1); sem Firefox/Safari.
